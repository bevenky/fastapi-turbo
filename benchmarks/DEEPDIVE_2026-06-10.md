# Performance Deep-Dive — 2026-06-10

Investigation of the latency regression flagged against the June-1 baseline
(trivial Python handler 23µs → 27µs, 20-item JSON 39µs → 43µs) plus a fresh
four-framework comparison matrix. Outcome: **two real bugs found** (one major —
orjson silently dead on every dict/list response), fixes applied on
`rewrite/dispatcher-collapse` (`src/responses.rs`, `src/streaming.rs`,
`python/fastapi_turbo/responses.py`), and the remaining gap attributed
microsecond-by-microsecond with env-gated Rust phase timers (instrumentation
since reverted).

---

## 1. Comparison matrix

All servers solo-booted (one server resident at a time), loopback, compiled
`fastapi-turbo-bench` client (raw TCP, HTTP/1.1 keep-alive), fastapi-turbo
pinned to `workers=1`. Medians across runs; per-run p50 spread at conn=1 was
< 1µs for every cell in this table.

### conn=1 latency, p50 µs (20k requests, 3k warmup; 3 runs, 5 for turbo)

| endpoint | raw Axum | Fastify 5 | fastapi-turbo | Go Gin |
|---|--:|--:|--:|--:|
| `/_ping` (static JSON) | 14.8 | 18.2 | **16.0** | 21.8 |
| `/hello` (trivial dict) | 14.9 | 19.4 | **22.0** | 22.3 |
| `/list` (20-item JSON) | 16.4 | 20.4 | **25.6** | 27.8 |
| `POST /items` (body validate) | 17.2 | 20.3 | **32.4** | 24.4 |

Delta vs each framework's own `/_ping` (isolates per-endpoint work from the
HTTP floor):

| endpoint | raw Axum | Fastify | fastapi-turbo | Gin |
|---|--:|--:|--:|--:|
| `/hello` | +0.1 | +1.2 | **+6.0** | +0.5 |
| `/list` | +1.6 | +2.2 | **+9.6** | +6.0 |
| `/items` | +2.4 | +2.1 | **+16.4** | +2.6 |

Reading: fastapi-turbo's Rust floor (`/_ping`, zero Python) is 1.2µs off raw
Axum and beats Fastify and Gin. Everything above the floor is the
Python-crossing cost — and §2 accounts for it to the tenth of a microsecond.
`/hello` and `/list` now match or beat Gin; `/items` is the remaining laggard.

For context: stock FastAPI+uvicorn measured ~190µs p50 on equivalent endpoints
(curated matrix in `latest_bench.md`, Apr 2026) — fastapi-turbo is ~8.6× faster
on `/hello` and within 1.5× of raw Axum.

### conn=8, p50 µs / req/s (40k requests, 4k warmup, 3 runs, medians)

| endpoint | raw Axum | Fastify | fastapi-turbo | Gin |
|---|--:|--:|--:|--:|
| `/_ping` | 55 / 125k | 75 / 83k | **49 / 136k** | 66 / 102k |
| `/hello` | 49 / 139k | 73 / 85k | **94 / 71k** | 67 / 100k |

| `/items` | 55 / 127k | 92 / 65k | **134 / 51k** | 71 / 90k |

Reading: the pure-Rust path scales like raw Axum (`/_ping` 136k vs 125k req/s).

`app.run()` defaults to multi-worker (fd-passing acceptor, one process per
core), and the prior perf audit measured ~linear multi-process scaling, so the
production configuration recovers the gap; these runs pin `workers=1`
deliberately to expose per-request cost.

| phase | µs |
|---|--:|
| pre-GIL + body read + `block_in_place` | 2.27 |
| **`set_request_scope_ctxvar`** | **5.55** |

### Suspects cleared

`drain_background_tasks` thread-local borrow + `apply_injected_response` check
+ `ROUTE_DEFAULT_STATUS` lookup ≈ **0.06µs combined**. The recently added
per-request bookkeeping is not a bottleneck.

### Bug 1 (the `/list` gap): orjson was silently dead — FIXED

`src/responses.rs::orjson_kwargs` built `{"default": _json_default}` with a
**non-interned** key string. orjson matches kwarg names by pointer identity
against interned strings, so *every* `orjson.dumps` call raised
`TypeError: unexpected keyword argument` — every dict/list response paid a
failed call + swallowed exception, then fell back to the handwritten Rust
writer (10.4µs for `/list` vs orjson's 0.69µs). Fix:
`pyo3::intern!(py, "default")`. Companions: PyBytes fast path in
`dict_to_json_bytes` (PyO3's `extract::<Vec<u8>>` iterates ~15ns/byte;
`as_bytes().to_vec()` is a memcpy) and PyBytes-first ordering in
`streaming.rs::python_val_to_bytes` (was paying a String-extract exception per
chunk). Consequence fix: `responses.py::_json_default` now mirrors
`write_any_json` semantics (set→list, whole-second timedelta→int,
`model_dump(mode="json")`, `vars()`) — verified against the upstream FastAPI
suite (10 tests fail without it once orjson is actually live).

### Bug 2 (the `/hello` gap): per-request scope ctxvar publish — quantified, fix designed

`router.rs::set_request_scope_ctxvar` publishes method/path/query/endpoint/
route-path into a Python contextvar on **every request** so exception handlers
and the Sentry glue can see request context. Cost: 4.4–5.5µs/request. An
env-gated skip experiment confirmed `/hello` drops to ~20µs without it.

## 3. Ranked bottlenecks and fix candidates

| # | bottleneck | cost | fix | est. gain |
|---|---|--:|---|--:|
| 1 | `set_request_scope_ctxvar` — eager Python call per request | 4.4–5.5µs **every Python endpoint** | Stash scope fields in a Rust thread-local; expose a small `#[pyfunction]` that `_invoke_exception_handler`/Sentry glue pulls **lazily** (errors are rare; success path pays zero Python). Interim cheap step: precompute endpoint + route-path `PyString`s into `RouteState` at startup and call positionally (−0.6µs). | **−4µs**: `/hello` 22→~18, `/list` 25.6→~22, `/items` 32.4→~28 |
| 2 | `/items` extraction plumbing (multimap parse, header walk, kwargs assembly — *not* pydantic, which is 0.37µs) | ~2.6µs + 2.3µs body-path pre-work | Skip query multimap when query string empty; pre-size kwargs dict; single-body-param fast path that hands bytes straight to `validate_json` without the generic param loop | −2–3µs on body endpoints |
| 3 | GIL detach on exit | 1.15µs | PyO3 floor (~2µs/acquisition round-trip per prior audit) — only recoverable by batching more work per GIL window; accept for now | 0 (floor) |
| 4 | Empty-query multimap parse | ~0.2µs | Length check before parse | −0.2µs |
| 5 | conn=8 GIL serialization (1 worker caps at 51–71k req/s) | throughput, not latency | Already mitigated: `app.run()` defaults to multi-worker; ~linear scaling measured in prior audit | n/a |

Projected conn=1 p50 after #1+#2: `/hello` ≈18µs (within 3µs of raw Axum,
ahead of Fastify), `/items` ≈27–28µs.

## 4. Methodology & variance

- **Machine**: Apple M5 Max, macOS (Darwin 25.5.0), loopback, *not* an isolated
  box. Conn=1 drift between server boots: ±1–2µs; deltas-vs-own-ping are the
  robust cross-framework metric.
- **Client**: `target/release/fastapi-turbo-bench` — raw TCP, keep-alive, one
  thread per connection, client-side histogram. (httpx/ASGITransport remain
  invalid for absolute numbers per the earlier audit.)
- **Protocol**: every cell = median of 3 independent runs (5 for turbo conn=1);
  20k requests / 3k warmup at conn=1, 40k / 4k at conn=8. Servers booted
  **solo** for the canonical tables. A co-resident cross-check (all four
  servers up simultaneously, reps interleaved across servers) reproduced the
  same rank order with fastapi-turbo cells ~3–5µs higher and fastify conn=8
  spread up to ±70µs — solo numbers are the ones to quote.
- **Configuration**: fastapi-turbo `app.run(host, port, workers=1)` (the new
  multi-worker default is great for production but wrong for per-request
  latency measurement — `run_bench.py` now pins this); uvicorn comparison not
  re-run (see `latest_bench.md` for the ~190µs reference).
- **Versions**: Python 3.14.4 (GIL build) · rustc 1.93.0 · axum 0.8.9 ·
  go 1.26.2 / gin 1.10.0 · node 25.9.0 / fastify 5.8.5 · fastapi 0.136.0
  (uvicorn leg reference).
- **Endpoint parity**: `/_ping` returns the identical static JSON body from all
  four servers; `/hello`, `/list`, `/items` follow the `_bench_app.py` contract
  (gin/fastify/axum mirrors updated in this change to match —
  `benchmarks/go-gin/main.go`, `benchmarks/fastify/server.js`,
  `comparison/rust-axum/main.rs`).
