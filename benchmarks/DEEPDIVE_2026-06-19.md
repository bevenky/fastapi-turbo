# Performance Deep-Dive — 2026-06-19

Apples-to-apples cross-framework benchmark **with streaming now measured on
all five frameworks**, plus a microsecond-by-microsecond attribution of every
turbo endpoint's per-request cost (env-gated Rust phase timers in
`handle_request` / `create_streaming_response` / the generator-iteration loops,
since reverted and **not** committed).

This closes the gap left by `DEEPDIVE_2026-06-15.md §Streaming`, where the
streaming row was turbo-vs-uvicorn ONLY (gin/fastify/axum showed `n/a`). All
six server processes now expose a **byte-identical** 10-chunk stream: 640 bytes,
sha256 `837aad5a…`, `Content-Type: text/plain; charset=utf-8`, chunked — verified
this session against all six.

**Method (strict).** Solo-boot ONE server at a time, killed before the next; all
five bench ports verified free before/after. conn=1 latency: N=20000 W=3000,
median of 3 (5 for turbo across sessions). Client:
`target/release/fastapi-turbo-bench --format json` (raw TCP, HTTP/1.1
keep-alive; it drains the whole chunked body, so its streaming number is a
**total**, not TTFB). Streaming TTFB measured separately with a raw-socket probe
(`/tmp/stream_ttfb.py`) that timestamps the first body byte after headers vs the
last chunk. Python servers 1 worker (turbo `app.run(workers=1)`, uvicorn
`--workers 1`). Phase timers: `FASTAPI_TURBO_PROFILE=1` accumulated per-phase ns
into a global histogram, dumped as percentiles — TEMPORARY, reverted before
commit (`git status` clean; only this doc added).

> **`/_ping`** is turbo's built-in pure-Rust route (not in the FastAPI app), so
> **uvicorn returns 404 for it** — uvicorn's floor reference is `/hello` (its
> lightest *defined* endpoint). raw-axum/gin/fastify replicate `/_ping` as a
> static string.

---

## 0. Headline

- **turbo wins the HTTP floor**: `/_ping` is the fastest of all five at conn=1
  (16.9µs vs raw-axum 17.5, fastify 20.8, gin 22.9) and ties raw-axum on conn=8
  throughput (~157k rps). Its pure-Rust path is at the Axum metal.
- **Every endpoint that crosses into Python pays one GIL round-trip + an
  extraction/serialize tax that the compiled frameworks don't have.** That tax
  is the *entire* gap to gin/fastify/axum on `/hello`/`/list`/`POST /items`
  (+4–13µs), and it is mostly irreducible (the GIL detach + PyO3 call floor is
  ~2µs; pydantic body validate is ~4.7µs of pure Python-side work).
- **Streaming, now apples-to-apples, is turbo's weakest area.** turbo's best
  stream path (`stream-async`, 92µs total / 47µs TTFB) is **2.3–4.7× behind**
  the compiled stream primitives (axum 19µs, gin 40µs, fastify 41µs), and at
  conn=8 its streaming throughput even **loses to uvicorn**. Mechanism: turbo
  flushes each chunk through an mpsc channel individually (48µs tail across 10
  chunks); the compiled frameworks and uvicorn-async coalesce all 10 chunks into
  ~one TCP write (tail ≈ 0.5µs).
- **vs uvicorn (same FastAPI app): 4.7–6.8× faster on every non-streaming
  endpoint**; on streaming turbo wins sync, ties await, and **loses async**.

## 2. Per-endpoint µs attribution (turbo)

Server-side phase timers, conn=1, 20000 req, p50 ns → µs. Phases:
`preGIL` (pure-Rust query/header/body parse before the GIL) · `attach` (GIL
acquire; ~0 on the single-`with_gil` fast path, ~1.3µs when wrapped in
`block_in_place`) · `extract` (`extract_params_to_pydict_full` — kwargs build +
pydantic validate) · `call` (the Python handler) · `serialize`
(`py_to_response` → `write_dict_json`). **These are server-internal and exclude
the ~16µs TCP/HTTP floor** the client's wall-clock latency also pays.

| turbo endpoint | preGIL | attach | extract | call | serialize | server p50 | client p50 |
|---|--:|--:|--:|--:|--:|--:|--:|
| `/hello` | 0.21 | 0.17 | — | 1.88 | 0.29 | **3.7** | 22.8 |
| `/list` | 0.21 | 0.17 | — | 3.42 | 0.92 | **6.3** | 24.7 |
| `POST /items` | 0.46 | 1.29 | 4.75 | 0.21 | 0.29 | **8.6** | 30.3 |

Reading each row:

- **`/hello`** — server work is 3.7µs; the rest of the 22.8µs client latency is
  the HTTP floor (`/_ping` = 16.9µs floor + the ~2µs sync-handler delta is the
  `attach`+`call`+`serialize` above the pure-Rust route). `call`=1.88µs is the
  bare Python function-call cost (CPython frame + return a 1-key dict). `attach`
  is only 0.17µs because the zero-param path uses a **single** `Python::with_gil`
  with no `block_in_place` wrapper. **Everything here is irreducible:** you can't
  invoke a Python function for less than one GIL acquisition + one CPython call.
- **`/list`** — identical shape to `/hello` but `call` rises to 3.42µs (building
  a 20-element list of 2-key dicts in Python) and `serialize` to 0.92µs (the
  larger JSON through `write_dict_json`). The +1.5µs `call` and +0.6µs serialize
  vs `/hello` are *Python object construction*, not framework overhead — gin
  pays the same kind of cost (its `/list` delta is +6.4µs, larger than turbo's
  +7.8 only because gin's floor is higher).
- **`POST /items`** — the body route. `attach`=1.29µs (this path runs inside
  `block_in_place`, which parks the tokio worker and is more than the bare
  `with_gil`), and `extract`=4.75µs dominates: that's the kwargs-dict build +
  `__pydantic_validator__.validate_json(bytes)` + constructing the `Item` model
  in Rust-driven pydantic. `call`=0.21µs (the handler just reads 3 attrs). So
  the body tax is **GIL-in-block_in_place (1.3µs) + pydantic validate/extract
  (4.75µs)** — this is why `/items` is turbo's worst delta-vs-ping (+13.4µs).

### What the gap to each competitor actually is

- **vs raw-axum** (the metal): the floor is a near-tie (`/_ping` 16.9 vs 17.5 —
  turbo wins). On `/hello`/`/list`/`/items` the *entire* delta is the
  Python-crossing: ~2µs irreducible GIL+call floor on GET, ~6µs
  validate+block_in_place on POST. Axum serializes via `serde` in-thread with no
  GIL; turbo's only way to beat that is to not enter Python — which it already
  does for `/_ping`.
- **vs go-gin**: turbo's pure-Rust floor (16.9) is *below* gin's (22.9), so turbo
  **wins `/hello` and `/list` outright on absolute latency** despite paying the
  GIL, because gin's per-request Go/net-http floor is ~6µs higher than turbo's
  Axum floor. gin only pulls ahead on `POST /items` (its `binding:"required"`
  JSON decode is ~2µs vs turbo's 4.75µs pydantic).
- **vs fastify**: fastify's V8-JIT + schema-compiled JSON serializer is the
  managed-runtime ceiling. It beats turbo on `/hello` (−1.7 delta vs +5.9) and
  `/items` because its floor (20.8) is close to turbo's and it pays no GIL. turbo
  ties/edges it on `/list` at conn=8.

**Irreducible vs addressable on the non-streaming rows:**
- Irreducible: GIL acquire+release (~1.15µs detach measured prior sessions) +
  one CPython call (~0.7–1µs frame setup) ≈ **~2µs/request floor** on any
  Python endpoint. This is the `/hello` delta and it cannot be removed without
  leaving Python.
- Addressable: the `block_in_place` `attach` cost on the body path (1.29µs vs
  0.17µs on the zero-param path) and part of the 4.75µs extract — see §4.

## 3. Streaming mechanism — where every µs goes

The contract is 10 chunks, no artificial delay, so this measures pure framework
*streaming overhead*, not I/O. Server-side stream timers (p50):

| turbo path | stream_setup | body production (off-thread) | per chunk |
|---|--:|--:|--:|
| stream-async | 1.75µs | `async_drive` = 48.9µs | ~4.9µs |
| stream-await | 2.21µs | `async_drive` = 215µs | ~21.5µs |
| stream-sync | 2.33µs | threadpool-wrapped → `async_drive` = 790µs | ~79µs |

`stream_setup` (GIL-bound: read status/headers, grab `body_iterator`, build the
mpsc channel, spawn the blocking task) is cheap and uniform (~2µs). All the cost
is in **body production**, which runs in a `spawn_blocking` task driving the
Python generator and pushing each chunk through a `tokio::mpsc` channel that
hyper drains onto the socket.

### sync-gen (`/stream-sync`, 830µs) — the threadpool tax

A `def gen(): yield ...` handed to `StreamingResponse` is wrapped by **Starlette**
in `iterate_in_threadpool`, turning it into an *async* generator whose every
`__anext__` hops to an anyio worker thread. So the "sync" stream actually takes
turbo's **async** driver (`async_drive`=790µs), and each chunk pays a full
thread-pool round-trip (~79µs/chunk). turbo (830) beats uvicorn (886) here by
~56µs because turbo's single-`run_until_complete` driver amortizes the loop
machinery, but **both are 20–43× slower than the compiled primitives** — this is
a Starlette design cost, not a turbo cost, and it's why real token streams should
use `async def gen`.

### async-gen no-await (`/stream-async`, 92µs total / 47µs TTFB) — the best path

`async def gen(): yield ...` (no `await` between chunks) runs under turbo's
single-driver: ONE `loop.run_until_complete(_drive_stream(aiter, push))` consumes
the whole iterator, handing each item to the Rust `ChunkPush.__call__`, which
`blocking_send`s it onto the mpsc channel (GIL released across the send).
`async_drive`=48.9µs for all 10 chunks ≈ 4.9µs/chunk: one async-generator
`__anext__` step (~3µs of asyncio + CPython) + the channel push + a hyper poll.

**Why it still loses to axum/gin/fastify (19–41µs):** the compiled frameworks
produce all 10 chunks with zero per-chunk scheduling — axum's `stream::iter` is a
plain Rust iterator, fastify's `Readable.from(gen())` runs in V8 with no GIL. And
critically (TTFB/tail data): **axum and fastify coalesce the 10 chunks into ~one
TCP write (tail 0.5µs)**, whereas turbo's mpsc→ReceiverStream flushes each chunk
as hyper polls it (tail **48µs**). uvicorn-async also coalesces (tail 0.6µs)
because its ASGI loop buffers the whole body before the first `http.response.body`
flush — which is why **uvicorn-async TTFB (107µs) ≈ its total**, while turbo
streams progressively (TTFB 47µs, much better, but pays a 48µs tail). On *total*
turbo-async (92) beats uvicorn-async (104); on *TTFB* turbo wins decisively
(47 vs 107) — the right metric for real token streaming. But head-to-head on the
synthetic no-delay total, turbo loses to all three compiled.

### async-gen with await (`/stream-await`, 277µs) — event-loop scheduling

Adding `await asyncio.sleep(0)` between chunks forces a real event-loop
reschedule per chunk: `async_drive`=215µs ≈ 21.5µs/chunk (vs 4.9µs no-await).
The +16.5µs/chunk is the asyncio scheduler round-trip (`sleep(0)` yields to the
loop, which re-polls the ready queue and resumes the gen). turbo (277) ≈ ties
uvicorn (269) here — both pay the same asyncio cost, and it is **irreducible**
for any Python async generator that actually suspends. The compiled frameworks
have no event loop in the per-chunk path, so they're 7–14× faster. **Real LLM
token streams are await-dominated** (each token awaits the model), so this is the
representative shape — and turbo matches uvicorn on it.

### conn=8 streaming collapse

At conn=8 turbo's streaming throughput is its single worst result:
async 6.6k rps (loses to uvicorn 13.9k!), await 3.7k (loses to uvicorn 8.2k).
Mechanism: every concurrent stream owns a `spawn_blocking` thread driving its own
`run_until_complete` on a thread-local event loop, and all of them contend on the
**one GIL**. uvicorn runs all streams on a *single shared* event loop (cooperative,
no thread-per-stream, no block_in_place), so under concurrency its async I/O
multiplexes better than turbo's thread-per-stream + GIL model. This is the
clearest addressable streaming defect (§4 #1).

## 4. Where we match / where we trail — ranked remaining addressable fixes

### Match (and how)
- **`/_ping` conn=1 + conn=8**: fastest / ties raw-axum. Pure Rust, no GIL — the
  Axum/hyper floor is the floor.
- **`/hello`, `/list` vs gin**: turbo wins on absolute latency because its Axum
  floor (16.9) undercuts gin's net-http floor (22.9) by more than the GIL tax.
- **`stream-await` vs uvicorn**: tie (277 vs 269) — both bottlenecked on
  identical asyncio per-chunk scheduling.
- **everything vs uvicorn**: 4.7–6.8× faster on non-streaming; the door removes
  the entire ASGI/Starlette request-construction floor uvicorn pays (122µs on
  `/hello` alone).

### Trail, and why (irreducible vs addressable)
- **All JSON/body endpoints vs raw-axum**: irreducible GIL+call floor (~2µs GET)
  + pydantic validate (~4.75µs POST). Addressable slice below.
- **`POST /items` vs all compiled**: the +13.4µs delta = 1.3µs block_in_place
  attach + 4.75µs extract/validate + floor. Partly addressable (#2).
- **All streaming vs all compiled**: turbo's best (async, 92µs) is 2.3–4.7×
  behind; the per-chunk mpsc flush tail (48µs) and per-chunk asyncio cost are the
  causes. The asyncio cost is irreducible for Python; the flush tail and the
  conn=8 thread-per-stream model are addressable (#1).

### Ranked addressable fixes

| # | fix | mechanism / evidence | est. gain |
|---|---|---|---|
| 1 | **Shared-loop streaming + chunk coalescing.** Drive all concurrent async streams on ONE shared event loop (as uvicorn does) instead of one `spawn_blocking` + thread-local loop per stream; and batch ready chunks into a single channel send / TCP write when the producer outruns the consumer (kills the 48µs per-chunk flush tail). | conn=8 streaming loses even to uvicorn (6.6k vs 13.9k) because of thread-per-stream GIL contention; tail=48µs (turbo-async) vs 0.5µs (axum/fastify) is the per-chunk flush. | conn=8 async ~2–3× (toward uvicorn+); conn=1 async total −30–48µs (toward ~50µs, near gin/fastify) |
| 2 | **Single-body-param extract fast path.** When a route has exactly one body param and no query/header/path params, skip the generic `extract_params_to_pydict_full` loop: hand raw bytes straight to the cached `validate_json` and build a 1-key kwargs dict. (Carried over from 06-15 #2; still open.) | `/items` extract=4.75µs wraps a ~0.4µs validate in multimap/kwargs scaffolding. | −2–3µs on body routes → `/items` ≈ 27–28µs (closing on gin 24.7) |
| 3 | **Avoid `block_in_place` on the single-body-param path.** The body path's `attach`=1.29µs vs 0.17µs on the zero-param `with_gil` path — the `block_in_place` wrapper costs ~1.1µs. A body-only sync route with no concurrency-sensitive await could use the bare `with_gil` fast path. | §2 attach column: 1.29 (block_in_place) vs 0.17 (with_gil). | −1µs on sync body routes |
| 4 | GIL round-trip + CPython call floor (~2µs). | §2 `/hello` delta. | 0 — irreducible; only recoverable by not entering Python (`/_ping`). |
| 5 | asyncio per-chunk scheduling on await-streams (~16.5µs/chunk). | §3 stream-await. | 0 — irreducible for any suspending Python async gen; turbo already ties uvicorn. |

**Projected after #1+#2:** `stream-async` conn=1 ≈ 50–60µs (within reach of
gin/fastify's 40µs), conn=8 streaming ≈ uvicorn or better; `POST /items` ≈ 27µs.
The remaining GET-shape gap to raw-axum (~2µs) is the GIL floor and is the price
of running real Python handlers at all.

## 5. Methodology & integrity

- **Machine**: Apple M-series, macOS (Darwin 25.x), loopback, not isolated.
  Same-session: all five frameworks booted/killed sequentially in one window;
  ports 8001/8002/8003/8004/8099 verified free before and after (confirmed at
  end). No two servers ever co-resident (the +3–5µs co-resident inflation was
  respected).
- **Byte-identity**: every `/stream*` endpoint across all 6 processes returns
  640 bytes, sha256 `837aad5a…`, `text/plain; charset=utf-8`, chunked — verified
  this session via curl against all six.
- **Phase timers**: `FASTAPI_TURBO_PROFILE=1`-gated, accumulated into a global
  ns histogram printed as percentiles. Added to `src/router.rs` /
  `src/streaming.rs` ONLY for this measurement and **reverted before commit**
  (working tree clean apart from this doc).
- **TTFB probe**: raw socket, single keep-alive connection, 400 samples after 50
  warmup, median; timestamps the first body byte after `\r\n\r\n` vs the chunked
  terminator. The bench client cannot do this (it drains the whole body), so the
  probe is the source for the tail/TTFB table in §1.
- **Versions**: Python 3.14 (GIL build) · FastAPI 0.136.0 · uvicorn 0.44.0 ·
  go/gin (release) · node 25.9 / fastify 5 · raw Axum 0.8.
- **Config**: turbo `app.run(host, port, workers=1)` (single-process, no fork);
  uvicorn `--workers 1 --no-access-log`. Identical `_bench_app.py` under both.
