How a request travels the
Python ⇄ Rust boundary

A visual map of where every request spends its time, what the GIL is doing at each step, and the concrete path to multi-core, Go-class throughput — without rewriting every layer in Rust, and without breaking drop-in FastAPI compatibility.

★The one fact that explains everything below
The Rust layer owns the network, routing and JSON. Every handler and every database driver (psycopg3, redis-py, SQLAlchemy) is Python. Database I/O never enters Rust — src/db_pool.rs is dead code; db.py imports the real psycopg_pool / redis-py (db.py:40, 235). And db.py ships sync helpers only — the async paths below are the user bringing their own async driver. So performance comes down to one question per request: does the Python code hold or release the GIL, and how many threads can run Python at once?

Section V2

Making it multi-core — the deep dive worth doing

How to get Go-class, multi-core throughput without bloating the Rust layer or rewriting every layer from scratch — while keeping import fastapi_turbo as fastapi the only line a user changes, and dropping a lot of what's there today.

!The constraint, stated precisely
Go runs your handler on any of N OS threads across N cores with no global lock. fastapi-turbo runs handler / driver / validation in Python, and CPython's GIL allows one thread to execute bytecode at a time. The Rust core already has a multi-threaded tokio runtime (server.rs:434, worker_threads = cores) — so the parallel machine is already there; the GIL is the lock sitting on top of it. You do not need to rewrite layers in Rust. You need to remove or sidestep the single-Python-thread bottleneck.

Three ways out — ranked

Option B · ship now

Pre-fork worker processes

N processes, each its own GIL, sharing one listening socket via SO_REUSEPORT; the kernel load-balances connections.
  • True multi-core today — N processes = N cores running Python in parallel.
  • Zero changes to the request path, the GIL story, or drop-in compat.
  • How Gunicorn/uvicorn already scale; well-understood ops model.
  • Shared-nothing — no shared in-memory cache/state across workers (use Redis).
  • ~N× memory; per-process warmup.
Surface: app.run(workers=N) → bind with SO_REUSEPORT in server.rs and fork, or document gunicorn -w N. Small Rust change, no rewrite.
Option A · endgame

Free-threaded Python (3.13t / 3.14t)

Run on a no-GIL build. attach becomes a cheap per-object lock, not a global one — the N tokio threads finally run Python in parallel on N cores, in one process.
  • The only option that truly matches Go: shared memory + linear CPU scaling, single process.
  • Keeps in-process shared state (caches, pools).
  • Lets you delete the single async-worker loop → one loop per worker thread.
  • Minimal new Rust — the runtime changes, not the architecture.
  • Needs C-ext safety: pydantic-core, psycopg, etc. free-threading-ready (landing).
  • Audit global RwLock<Option<Py>> statics (router.rs:29-33) & the HANDLER_CLASS mutex.
  • orjson may be absent → the hand-rolled JSON path must stay byte-identical.
Surface: build/test on 3.14t; per-thread event loops; concurrency-audit the statics. AUDIT.md §3, §6.
Option C · partial

Event-loop pool (one per thread)

Replace the single shared _async_worker loop with one loop per tokio worker thread, so async requests spread across threads.
  • Removes the “all async CPU on one thread” wall (cards 4 & 6).
  • Helps even with the GIL by overlapping I/O better.
  • Does not break the GIL — CPU still serializes globally until you also do A.
  • More moving parts; only a partial win alone.
Best used as: the bridge that makes Option A pay off — under no-GIL, per-thread loops give linear async scaling. Do C as part of A, not instead of it.
▸Recommended sequencing — “drop code, don't rewrite layers”
  1. Now (Option B): add app.run(workers=N) via SO_REUSEPORT pre-fork. Instant multi-core for every path in V1, zero request-path risk, fully drop-in. Ship the “matches Go under load” story today.
  2. Next (Option A + C together): make the build run on free-threaded 3.14t; replace the single shared loop with per-thread loops; concurrency-audit the global statics. The single-process, shared-memory match to Go.
  3. Then delete: once B+A exist, large amounts of current code stop carrying weight and can go (below).

▤The rule that makes it safe
The plane stores Rust-owned bytes & atomics — never live Python objects (those can't cross the boundary safely). Each worker pulls from the plane and builds its own per-request Python objects. That single rule is what turns "shared memory" from hand-waving into something sound. Under free-threaded Python (V2 Option A) the plane is direct shared-heap — literally Go's sync.Map / sync/atomic / channels. Under pre-fork it's a shared-memory segment + a tiny in-Rust broker for pub/sub.

▸How this reaches Go-level — the two moves together
  1. Shrink the GIL path (this section): push everything except the handler body + DB call into Rust. Now each request holds the GIL only for irreducible Python, and shared state is correct & in-memory. This maximizes per-core throughput and fixes correctness — but CPU still serializes on one GIL.
  2. Parallelize the remainder (V2 Option A · free-threaded): with the path already this thin, the only thing left under the GIL is the handler + pydantic — and free-threaded Python runs those across all N cores in one address space, reading the same Rust plane with zero IPC. Thin GIL path + true parallelism = Go's model: one process, one shared (Rust) heap, N cores, no Redis.

Until free-threaded is production-ready, pre-fork (V2 Option B/D1) + the shared-memory plane gives you correct shared state and near-linear cores today — and the request path above doesn't change when you flip to free-threaded. You build it once.

Deep-dive checklist — what to investigate, in order

  1. Measure the real gap first. Benchmark the same app under (a) app.run() single process, (b) SO_REUSEPORT ×N processes, (c) a suspending async-DB endpoint vs a sync-DB one. The V1 cards predict the shapes; confirm them. AUDIT.md §8.
  2. Prototype SO_REUSEPORT pre-fork in server.rs behind app.run(workers=N). Verify linear scaling on the pure-HTTP and async-DB cards. Cheapest multi-core win; de-risks everything else.
  3. Stand up a free-threaded 3.14t build in CI. Re-measure the old “3.5× slower” no-GIL number on PyO3 0.28 — it predates the current code. Find the orjson-absent JSON penalty.
  4. Concurrency-audit the Rust globals for real parallel attach: APP_INSTANCE / VALIDATION_HANDLER (router.rs:29-33), the HANDLER_CLASS mutex (poison + pointer-key), per-request OnceLock caches.
  5. Replace the single loop with per-thread loops (Option C) and re-run the async-DB card — where async SQLAlchemy/psycopg should start scaling.
  6. Build the Rust-vs-Python engine diff test (AUDIT.md P0) before deleting the in-process dispatcher, so the collapse is provably parity-preserving.
  7. Confirm C-ext free-threading readiness for your stack: pydantic-core, psycopg(3), redis-py, SQLAlchemy. Where a dep isn't ready, pre-fork (B) is the fallback — B and A coexist, not compete.
★One-line strategy
B now for instant multi-core at zero risk, A + C next for the true single-process Go-class model, and use the headroom to delete ~7,500 LOC — all while import fastapi_turbo as fastapi stays the only line a user changes.
